# Simple Music 项目容器化部署指南

> 记录将 vibe-music 全栈项目（Spring Boot + Vue + MySQL + Redis + MinIO）容器化的完整过程，包括踩坑记录与解决方案。

## 三、Dockerfile 编写要点

### 3.1 前端项目（Admin / Client）—— 多阶段构建

```dockerfile
# ===== 第一阶段：构建 =====
FROM node:20-alpine AS builder
WORKDIR /app
RUN corepack enable && corepack prepare pnpm@latest --activate
COPY package.json pnpm-lock.yaml ./
RUN pnpm install                     # 安装依赖
COPY . .                             # 复制源码
RUN pnpm build                       # 打包

# ===== 第二阶段：运行 =====
FROM nginx:alpine
COPY nginx.conf /etc/nginx/nginx.conf
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

**关键设计**：

- **多阶段构建**：构建阶段使用 Node.js 镜像（~180MB），运行阶段只保留 Nginx（~25MB），最终镜像体积大幅缩小
- **依赖安装与源码复制分离**：先 `COPY package.json` 再 `RUN pnpm install`，最后 `COPY . .`，这样源码变动不会导致重新安装依赖，利用 Docker 缓存加速构建
- **Corepack 管理 pnpm**：Alpine 镜像不自带 pnpm，通过 `corepack` 激活

### 3.2 后端项目（Spring Boot）—— 多阶段构建

```dockerfile
# ===== 第一阶段：构建 =====
FROM maven:3.9.9-eclipse-temurin-21 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline -B     # 预下载依赖
COPY src ./src
RUN mvn clean package -DskipTests    # 打包

# ===== 第二阶段：运行 =====
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**关键设计**：

- **Maven 依赖预下载**：先复制 `pom.xml` 执行 `dependency:go-offline`，Maven 依赖可能有几百 MB，这样源码变动不会重新下载
- **JRE 替代 JDK**：运行阶段只需要 JRE（~170MB），不需要完整的 JDK + Maven（~800MB+）
- **跳过测试**：Docker 构建中跑测试非常慢，交给 CI 环境做

## 四、docker-compose.yml 配置要点

### 4.1 服务依赖与启动顺序

```yaml
backend:
  depends_on:
    mysql:
      condition: service_healthy    # MySQL 健康检查通过后才启动
    redis:
      condition: service_started    # Redis 启动即可

admin:
  depends_on:
    - backend                       # 简单依赖，不需要健康检查
```

### 4.2 MySQL 健康检查

```yaml
healthcheck:
  test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
  interval: 10s
  timeout: 5s
  retries: 5
```

MySQL 容器启动后需要一段时间初始化，健康检查确保后端连接时 MySQL 已就绪。

### 4.3 容器间网络通信

容器之间通过**服务名**互访，Docker 内部 DNS 自动解析：

```yaml
# 后端连接 MySQL（mysql 是服务名，不是 localhost）
- SPRING_DATASOURCE_URL=jdbc:mysql://mysql:3306/vibe_music

# 后端连接 Redis
- SPRING_DATA_REDIS_HOST=redis

# 后端访问宿主机 MinIO
- MINIO_ENDPOINT=http://host.docker.internal:9000
```

> `host.docker.internal` 是 Docker 提供的特殊域名，指向宿主机 IP。

## 五、踩坑记录与解决方案

### 坑 1：`vue-demi package.json file does not exist`

**现象**：admin 项目构建时 `vite-plugin-cdn-import` 报错

**原因**：`vue-demi` 是 `pinia` 的依赖，pnpm 的严格依赖隔离策略不会自动将其提升到顶层 `node_modules`。`vite-plugin-cdn-import` 插件需要读取 `vue-demi/package.json` 来获取版本号，但找不到该文件。

**解决**：在 `package.json` 的 `dependencies` 中显式添加 `vue-demi`：

```json
"vue-demi": "^0.14.10"
```

---

### 坑 2：`tippy.js/dist/tippy.css` 无法解析

**现象**：上一个问题修复后，构建仍然报错 `Rollup failed to resolve import "tippy.js/dist/tippy.css"`

**原因**：`vue-tippy` 依赖 `tippy.js`，但 `tippy.js` 未在 `package.json` 中显式声明。同样受 pnpm 严格依赖隔离影响，构建时无法找到该包。

**解决**：在 `package.json` 的 `dependencies` 中显式添加 `tippy.js`：

```json
"tippy.js": "^6.3.7"
```

---

### 坑 3：`ERR_PNPM_OUTDATED_LOCKFILE` lockfile 不同步

**现象**：添加依赖后 `pnpm install --frozen-lockfile` 报错

```
ERR_PNPM_OUTDATED_LOCKFILE  Cannot install with "frozen-lockfile" because
pnpm-lock.yaml is not up to date with <ROOT>/package.json
```

**原因**：修改了 `package.json` 添加了新依赖，但 `pnpm-lock.yaml` 还是旧的，`--frozen-lockfile` 严格模式拒绝安装。

**解决**：Dockerfile 中去掉 `--frozen-lockfile` 参数：

```dockerfile
# 修改前
RUN pnpm install --frozen-lockfile

# 修改后
RUN pnpm install
```

> 对于 Docker 构建场景，去掉 `--frozen-lockfile` 是更灵活的做法。如果要严格锁定版本，可以在本地先执行 `pnpm install` 更新 lockfile，再提交到仓库。

---

### 坑 4：MySQL 端口 3306 被占用

**现象**：`docker compose up` 报错

```
Error: ports are not available: listen tcp 0.0.0.0:3306: bind: Only one usage of each socket address
```

**原因**：宿主机已运行 MySQL 服务，占用了 3306 端口。

**解决**：修改 `.env` 中的 `MYSQL_PORT`：

```env
# 修改前
MYSQL_PORT=3306

# 修改后
MYSQL_PORT=3307
```

---

### 坑 5：`MYSQL_USER=root` 导致 MySQL 无法启动

**现象**：MySQL 容器不断重启，日志报错：

```
[ERROR] [Entrypoint]: MYSQL_USER="root", MYSQL_USER and MYSQL_PASSWORD are for
configuring a regular user and cannot be used for the root user
```

**原因**：MySQL 官方镜像的 `MYSQL_USER` 环境变量只能创建**普通用户**，不允许设为 `root`。root 密码必须通过 `MYSQL_ROOT_PASSWORD` 单独设置。

**解决**：

1. `.env` 中将 `MYSQL_USER` 改为普通用户名：

```env
# 修改前
MYSQL_USER=root

# 修改后
MYSQL_USER=vibe_music
```

2. `docker-compose.yml` 中后端使用 root 账号连接数据库：

```yaml
# 修改前
- SPRING_DATASOURCE_USERNAME=${MYSQL_USER}
- SPRING_DATASOURCE_PASSWORD=${MYSQL_PASSWORD}

# 修改后
- SPRING_DATASOURCE_USERNAME=root
- SPRING_DATASOURCE_PASSWORD=${MYSQL_ROOT_PASSWORD}
```

3. 清理旧的 MySQL 数据目录后重新初始化：

```bash
docker compose down
rm -rf ./data/mysql/*
docker compose up -d
```

---

### 坑 6：Redis 空密码导致启动失败

**现象**：Redis 容器不断重启

**原因**：`.env` 中 `REDIS_PASSWORD` 为空，`redis-server --requirepass ""` 会导致 Redis 启动失败。

**解决**：如果不需要密码，就不传 `--requirepass` 参数：

```yaml
# 修改前
command: redis-server --requirepass ${REDIS_PASSWORD}

# 修改后
command: redis-server
```

---

### 坑 7：Redis 环境变量名不匹配

**现象**：后端启动报错 `Unable to connect to Redis`

**原因**：`docker-compose.yml` 中的环境变量名与 `application.yml` 中的配置路径不匹配。

Spring Boot 的配置属性路径是 `spring.data.redis.host`，对应环境变量前缀为 `SPRING_DATA_REDIS_`，而不是 `SPRING_REDIS_`。

```yaml
# application.yml 中的配置
spring:
  data:
    redis:
      host: ${SPRING_DATA_REDIS_HOST:127.0.0.1}
      port: ${SPRING_DATA_REDIS_PORT:6379}
      password: ${SPRING_DATA_REDIS_PASSWORD:}
```

**解决**：

```yaml
# 修改前（错误）
- SPRING_REDIS_HOST=redis
- SPRING_REDIS_PORT=6379
- SPRING_REDIS_PASSWORD=${REDIS_PASSWORD}

# 修改后（正确）
- SPRING_DATA_REDIS_HOST=redis
- SPRING_DATA_REDIS_PORT=6379
- SPRING_DATA_REDIS_PASSWORD=${REDIS_PASSWORD}
```

> **经验**：Spring Boot 环境变量名必须与 YAML 配置路径完全对应，用 `_` 替换 `.`，全部大写。例如 `spring.data.redis.host` → `SPRING_DATA_REDIS_HOST`。

---

### 坑 8：MinIO 环境变量名不匹配

**现象**：MinIO 连接配置未生效（潜在问题）

**原因**：与 Redis 类似，`application.yml` 中读取的是自定义环境变量 `MINIO_ACCESSKEY` 和 `MINIO_SECRETKEY`，但 `docker-compose.yml` 传的是 `MINIO_ROOT_USER` 和 `MINIO_ROOT_PASSWORD`。

```yaml
# application.yml 中的配置
minio:
  endpoint: ${MINIO_ENDPOINT:http://127.0.0.1:9000}
  accessKey: ${MINIO_ACCESSKEY:minioadmin}
  secretKey: ${MINIO_SECRETKEY:minioadmin}
```

**解决**：

```yaml
# 修改前（错误）
- MINIO_ROOT_USER=${MINIO_ROOT_USER}
- MINIO_ROOT_PASSWORD=${MINIO_ROOT_PASSWORD}

# 修改后（正确）
- MINIO_ACCESSKEY=${MINIO_ROOT_USER}
- MINIO_SECRETKEY=${MINIO_ROOT_PASSWORD}
```

### 坑 9：`Cannot read properties of undefined (reading 'split')`

**现象**：访问管理端 http://localhost:3000 时浏览器控制台报错

```
Uncaught TypeError: Cannot read properties of undefined (reading 'split')
```

**原因**：`.env.production` 中缺少 `VITE_ROUTER_HISTORY` 环境变量。代码中 `getHistoryMode(import.meta.env.VITE_ROUTER_HISTORY)` 接收到 `undefined`，随后调用 `.split(",")` 报错。

```typescript
// router/utils.ts
function getHistoryMode(routerHistory): RouterHistory {
  const historyMode = routerHistory.split(","); // undefined.split() 报错！
  // ...
}
```

**解决**：在 `.env.production` 中添加路由模式配置：

```env
VITE_ROUTER_HISTORY = "hash"
```

> **经验**：Vite 项目的所有 `import.meta.env.VITE_*` 变量在构建时被静态替换。如果 `.env.production` 中未定义，值会是 `undefined`，构建不会报错但运行时会崩溃。务必确保生产环境变量文件包含所有必要变量。

### 坑 10：`<img>` 标签引用 SVG 图片不显示

**现象**：登录页头像图片不显示，`<img :src="avatar1" class="avatar" />` 渲染为空

**原因**：项目使用了 `vite-svg-loader` 插件，它会把所有 `.svg` 导入**默认当作 Vue 组件**处理。直接 `import avatar1 from "@/assets/login/avatar.svg"` 拿到的是组件对象，而非 URL 字符串，`<img :src>` 无法使用。

```typescript
// vite-svg-loader 会拦截所有 .svg 导入，返回 Vue 组件
import avatar1 from "@/assets/login/avatar.svg"  // ← 返回的是组件，不是 URL！

// static.ts 中的用法是正确的——作为组件使用
import avatar from "@/assets/login/avatar.svg?component"  // 显式声明为组件
```

**解决**：加上 `?url` 后缀强制 Vite 返回资源的 URL 字符串：

```typescript
// 修改前
import avatar1 from "@/assets/login/avatar.svg"

// 修改后
import avatar1 from "@/assets/login/avatar.svg?url"
```

> **Vite SVG 导入后缀说明**：
>
> | 后缀 | 返回值 | 适用场景 |
> |------|--------|---------|
> | `.svg`（无后缀） | 被 `vite-svg-loader` 拦截，返回 Vue 组件 | 取决于插件配置 |
> | `.svg?component` | Vue 组件 | `<component :is="icon" />` 或 JSX |
> | `.svg?url` | URL 字符串 | `<img :src="url" />` |
> | `.svg?raw` | 原始 SVG 文本 | 需要操作 SVG 源码 |

## 六、数据库初始化

容器启动后数据库是空的，需要手动导入 SQL：

```bash
# 方式 1：通过 docker exec 导入（推荐）
cmd /c "docker exec -i mysql mysql -uroot -p123456 vibe_music < sql\vibe_music.sql"

# 方式 2：进入容器手动导入
docker exec -it mysql mysql -uroot -p123456 vibe_music
mysql> source /path/to/vibe_music.sql
```

> **Windows 注意**：PowerShell 不支持 `<` 重定向到 `docker exec`，需使用 `cmd /c` 包裹命令。

## 十、经验总结

1. **pnpm 严格依赖隔离**：pnpm 不会像 npm 那样扁平化 `node_modules`，未显式声明的依赖在构建时可能找不到。如果遇到 `Cannot resolve` 或 `package.json does not exist` 错误，先在 `package.json` 中显式添加该依赖。

2. **环境变量名必须与配置路径完全对应**：Spring Boot 的 `spring.data.redis.host` 对应环境变量 `SPRING_DATA_REDIS_HOST`，不是 `SPRING_REDIS_HOST`。建议先看 `application.yml` 中用的是什么变量名，再写 `docker-compose.yml`。

3. **MySQL 官方镜像的限制**：`MYSQL_USER` 不能设为 `root`，root 密码只能通过 `MYSQL_ROOT_PASSWORD` 设置。

4. **Vite 生产环境变量**：所有 `import.meta.env.VITE_*` 变量必须在 `.env.production` 中定义，否则构建后运行时会得到 `undefined`。开发环境有默认值不代表生产环境也有。

5. **PowerShell 的重定向限制**：Windows 下 PowerShell 不支持 `<` 输入重定向到 `docker exec`，需要用 `cmd /c` 包裹或使用管道方式。

6. **Docker 多阶段构建**：前端项目用 Node.js 构建、Nginx 运行；后端项目用 Maven/JDK 构建、JRE 运行。可以大幅减小最终镜像体积。

7. **容器间通信用服务名**：不要用 `localhost` 或 `127.0.0.1`，要用 `docker-compose.yml` 中定义的服务名（如 `mysql`、`redis`），Docker 内部 DNS 会自动解析。访问宿主机用 `host.docker.internal`。

8. **vite-svg-loader 与 `<img>` 冲突**：使用了 `vite-svg-loader` 插件后，所有 `.svg` 导入默认返回 Vue 组件。如果需要在 `<img :src>` 中使用 SVG，必须加 `?url` 后缀；作为组件使用时加 `?component` 后缀更明确。
